## Encryption and authenticated recovery — recorded before storage changes

Each issuance receives a random 256-bit data-encryption key (DEK). The server stores only AES-256-GCM escrow encrypted with a purpose-specific versioned server key from OFFLINE_RECOVERY_KEYS (JSON key-ID → base64 32-byte key), active ID OFFLINE_RECOVERY_ACTIVE_KEY. AAD binds issuance ID, actor kind/ID, Facility, Department, Neighborhood, Space, operational date and session version. No browser can request escrow plaintext directly. Production secret provisioning/rotation is a release prerequisite: retain prior server key IDs until their pending intent is reconciled; a missing key fails closed, never deletes history.

Preparation sends the DEK once over the authenticated no-store response. The original tab wraps it with its own random 256-bit wrapping secret kept in **sessionStorage only**; persist only wrapped DEK and ciphertext in IndexedDB. Import runtime keys non-extractable; no DEK, wrapping secret or CryptoKey is stored unwrapped in IndexedDB/CacheStorage/localStorage. This intentionally permits offline reload in that original authenticated tab, not offline login. A newly opened/opener-cloned tab must discard inherited wrapping material and obtain online authorization. Browser restart/session restoration is not an offline authentication guarantee.

Before any read/render/write, compare actor/session, Facility, Department, Neighborhood, Space, operational date, lease and shared sign-out generation. Sign-out, expiry or scope change erases that tab's wrapping secret, runtime keys and displayed data; cross-tab generation invalidates in-flight responses. Pending ciphertext and server escrow remain. No other actor/Facility context is given the old wrapping secret. **Only after this removal is pending intent called sealed/locked.** While the original tab is authorized it can decrypt its own cache; neither AES nor these application boundaries protect against compromised same-origin JavaScript, browser extensions or an attacker controlling the original live tab.

Recovery is online only: use the canonical credential login/PIN owners to issue a short-lived, HttpOnly HMAC authentication proof (not stored in offline storage). The recovery owner requires the same current actor, current lifecycle/session/Facility authority and an explicit reviewed-issuance consent. Its proof must be newer than preparation/last recovery and at most five minutes old; consume it for this issuance transactionally. Changing Facility or minting a context session alone cannot create this proof. Recover the existing DEK without extending the original lease. Expired intent is reviewable only after fresh online authentication; it cannot render operational instructions or create new offline actions. Reconnect revalidates every existing queued intent; review does not grant authority or silently refresh stale configuration. No password/PIN/JWT is put into cache, receipts or command payloads.

Full-unbind explicitly discloses the count and permanent local loss of pending actions before deleting local envelopes. Standard sign-out preserves them. Existing legacy IndexedDB is a separate compatibility store with its older device-key limitations: do not label it sealed, auto-import it as canonical intent or silently erase pending legacy commands. Existing server/domain history is preserved.

## Numeric bounds

- Lease: at most 12 hours, shortened by JWT expiry, effective Facility role end and assignment end when known; no offline renewal.
- Credential recovery proof: five minutes; newer-than-issuance/recovery, consumed per issuance. No offline unlock.
- Bundle: 512 KiB UTF-8; at most 250 Work and 250 Key Time targets. Preparation fails rather than truncating scope invisibly.
- Local canonical store: at most eight retained issuance envelopes, 200 commands total, 2 MiB ciphertext total; per command 8 KiB UTF-8 and note at most 1,000 characters. Fail before admission; never evict pending intent automatically. Full-store recovery uses online reconciliation and explicit removal of preparations with no pending actions, or explicit full-unbind with pending-loss disclosure. The 2 MiB bound measures serialized envelope UTF-8 bytes, not database-engine overhead.
- Sync/reconciliation: 20 commands/IDs per request, 192 KiB actual UTF-8 body; command version and strict field allowlists; bounded 30-second Serializable database transactions and the existing five positively confirmed rollback attempts. No retry of unknown COMMIT without same-ID receipt reconciliation.
- Server keyring: at most four 32-byte versioned keys. Metadata/IDs are bounded; no provider call or credential check occurs inside a domain mutation transaction.

## Operator recovery

Open the assigned current Space online and choose **Save on this tablet** before disconnecting. Prepared instructions are scoped to that Space; local actions remain pending until server confirmation. Reconnect and choose **Reconcile and sync pending actions**; do not create replacement command identities after an interrupted response.

If access is locked or expired, authenticate online using the original account and password/PIN method, return to the same Space, choose **Review locked pending intent online**, recover the intended issuance, inspect its labels/times/notes and explicitly submit reviewed intent. Recovery does not renew the old operational lease. Conflicts go through the existing online Work/Cycle owner; Key Time corrections and expected-time adjustments stay online-only.

**Lock offline access** clears local access and preserves encrypted pending intent. Use the existing Account menu to sign out online. Do not full-unbind a tablet with unresolved intent unless its disclosed local loss is intended. Preparations with no pending actions can be removed without discarding unresolved commands. Future public offline-code changes must advance the service-worker cache version; do not silently serve mixed script versions under a released cache key.

## Causal timing-adjustment fence — recorded before forward migration

A held-lock PostgreSQL regression demonstrated a real gap: a canonical timing adjustment committed during replay's lock wait, yet the older Serializable snapshot accepted an actual against the former reviewed timing. A lock without a parent-row change cannot refresh that snapshot. The failed reproduction is retained as `timing-wait-before.log`; it must not be counted as passing evidence.

The bounded correction adds `DepartmentOperationalCycle.timingAdjustmentRevision`, an existing-parent concurrency fence, through a separate forward migration. The canonical online timing owner increments it in the same transaction as its append-only adjustment, with Facility → Cycle lock order. Replay's existing Cycle share lock then detects a changed parent version and the existing confirmed-rollback retry obtains a fresh snapshot. Preserve publication status, definition version, published start/end/due values and published `updatedAt`; the counter is not another operational fact store or a permission. No changed retry limit, lower isolation, independent reader connection or applied-SQL edit. The failed reproduction and corrected observed-wait proof are retained. Current certification/inventory records the final gate result. The revision is a concurrency fence, not an audit count; zero on historical rows does not reinterpret earlier adjustments. All production timing writers must be upgraded before canonical offline is made available.

Facility timezone is also part of reviewed intent. A changed timezone requires renewed review rather than silently reinterpreting the captured instant in another local clock.
