## ONB-D05 — Employee update contract — accepted for ONB-01

Use a supplied-field patch, never a replacement record. Preserve all unprovided HR/contact/employment fields and relationship sets. New Employee creation remains rejected. Updating Facility Employee contact/name does not implicitly edit global User identity, link an account, or change access.

| Input | Planned effect |
|---|---|
| Column absent | Preserve field / membership set, including email, role, status, dates, and workstations |
| Blank or whitespace-only cell | Preserve; never null/default/revoke/reactivate implicitly |
| Explicit valid nonblank value | Validate and preview before/after; identical value is a no-op |
| Exact reserved token `__CLEAR__` after trimming | Clear only a field explicitly allowlisted below; show a clear operation in preview |
| Invalid enum/date/boolean, duplicate canonical header, truncated row, or extra populated cell | Row/header error; no default, truncation, or silent coercion |
| Ambiguous match, supplied stable ID/email disagreement, or supplied email matching nobody | Block the row; no fallback to a different person |

Clear allowlist for ordinary updates: nullable Facility Employee contact/HR fields `email`, `phone`, `hireDate`, `jobClassification`, `chrcStatus`, `chrcClearedAt`, `chrcNotes`, `birthMonth`, `birthDay`, `shirtSize`, `hrNotes`, and `primaryUnit`; `workStations` may explicitly clear to `[]`. Existing domain constraints still apply (e.g. paired birth fields or CHRC metadata). Employee email clear affects only that nullable contact field; it must not clear `User.email`, unlink `userId`, or bypass a requirement imposed by the effective role/action. Where the domain cannot safely express a clear, reject it with an actionable error. Required names, roleType, employmentType, status, identity/link/access keys, history and separation/offboarding facts are not clearable. `false` is an explicit boolean, never a blank default. The reserved token cannot also mean a literal text value in version 1.

Matching order: optional exported `employeeId` as an exact Facility-scoped existing ID; otherwise unique email. Names-only compatibility may match one unique first+last pair within the Facility only when neither stable ID nor email is supplied, and must show that match for review. No ambiguous or cross-Facility match; no names-based global User linking. Email edits should use stable Employee ID so the proposed email is not confused with the lookup email. File-local row references are not persistent identity.

Ordinary update mode may not terminate, reactivate/rehire, grant/revoke access, change platform authority, or rewrite separation history. An explicit changed role/status/lifecycle request must be a separately labeled, separately authorized domain operation with its full effects previewed. Until that operation is implemented through existing lifecycle/access/audit owners, reject the row and direct the operator to the existing profile/status/separation action. An unchanged supplied role/status is a no-op. Do not merely hide or ignore a requested transition. No import broadens the actor's existing authority.

Preview must show resolved employee, matching basis, exact changed/cleared fields, no-ops, warnings/errors, allowed rows, and transaction boundaries. It writes nothing. Confirm reauthorizes, reparses, rereads targets/dependencies and compares the reviewed plan under the mutation transaction's concurrency protection. Material change, revoked access, termination or new identity ambiguity requires renewed review. The reviewed intent is not permission to overwrite a newer record.

Retain per-employee transactions for the first protection slice unless a concrete domain reason requires a change. Each allowed row either commits its patch + required audit/revocation effects or rolls back. Show committed/no-op/blocked/failed counts and row results; other rows may already be committed. Retry only failed/uncommitted intent against a fresh preview, and treat already-applied patches as no-ops. Never claim file-wide rollback. ONB-01 must prove absent-field preservation, deliberate clear, pure preview, stale/ambiguous/wrong-Facility/Quick PIN denial and lifecycle/session safety with meaningful tests.

## ONB-D08 — ONB-01 implementation and release boundary — implemented

ONB-01 was explicitly authorized after ONB-00. It implements D05/D06 for **existing Employee updates only**. ONB-02 is not authorized by this execution. The accepted audit/plan and ONB-00 fixture/authority alignment are preserved.

- `src/lib/employee-csv-import.ts` now parses supplied-field intent without defaults. It accepts recognized legacy headers plus optional `employeeId`; blank means preserve. `__CLEAR__` follows D05, explicit false is a real boolean, invalid values are errors, and input is not silently truncated/coerced. Strict quoted/multiline CSV keeps physical row and original column/header provenance. The download contains headers only. Legacy role/status/separation columns are assertions when identical to stored values; changes are blocked and directed to existing actions.
- `src/lib/employee-csv-update/service.ts` owns this bounded update plan/confirm flow. Stable ID may propose a new unused contact email; an email already identifying another Employee blocks the row. Without stable ID, a supplied unmatched email never falls back to names. Duplicate target IDs or duplicate proposed emails block affected rows. Unique names are a Facility-only compatibility match, not global identity inference.
- A deliberate nullable Employee email clear never edits `User.email`, `Employee.userId`, accounts or grants. It is denied for password-required workforce or effective internal roles. Primary location resolves one active Facility location and respects existing restricted Unit access. Birthday edits must produce a valid pair. Date-only re-submission preserves the stored timestamp when its calendar day is unchanged.
- Preview uses reads only. The review token is purpose-separated HMAC-SHA256 using existing `AUTH_SECRET`, expires in 30 minutes, and binds actor, Facility, session version/role, template version, source bytes/hash, filename, row targets and reviewed plan/fact digests. No process-local receipt store, migration, source-file persistence, account creation, or additional import adapter was added.
- Confirmation reuploads/reparses the same UTF-8 source, verifies its review, and uses a **Serializable transaction per employee**. Actual User, Facility grant/role-period and Role rows are share-locked, and the scoped Employee is update-locked. Canonical live session/role validation runs after authority locks and again after dependency reads/row-lock waits, so a time-effective role expiring during a wait cannot authorize the write. Review expiry is rechecked after waiting. Match, complete Employee/membership facts, relevant credential policy and location dependencies are rebuilt; material drift requires renewed review. Serialization/deadlock conflicts are failed rows requiring review, not silent retries.
- Fingerprints exclude incidental Employee `updatedAt` and workstation membership creation timestamps; actual scalar/membership/security facts are included. A replay is unchanged only when the current facts exactly match the reviewed after-state and the intended patch is already a no-op. Newer different facts never get overwritten by a replay.
- Ordinary changes use the existing HR snapshot/diff helpers. The reviewed patch, explicit workstation replacement (only when supplied), field audit, and source/row/version/column receipt in `EmployeeHrAuditLog` commit together. The receipt's User FK is the live customer User. Console, Quick PIN, non-internal sessions and insufficient roles are rejected before reading the file; PlatformStaff is never inserted into a User FK. Dedicated staff attribution and generalized durable batch receipts remain ONB-04 work.
- The old immediate `importEmployeesFromCsvAction` entry point was removed. New actions return typed expected validation errors as data, following the installed Next.js guide, so production customers receive actionable file errors. Unexpected errors retain framework handling. Cache invalidation failure cannot obscure committed results; a lost network response directs the customer to reconcile roster/audit and preview again. The UI reports committed, unchanged, blocked and failed per row and states that there is no file-wide rollback.

The protection replaces the unsafe path without an opt-out flag. Rollout may disable intake if needed, but must not restore default-reset parsing or unreviewed mutation. Existing accounts, grants, PIN/session state, separation history and unrelated membership sets are preserved by ordinary updates; no historical backfill or publication is implied. Keep `AUTH_SECRET` stable across serving instances; rotation invalidates outstanding reviews and requires fresh preview. The phase's verification and stop boundary are recorded in the single tracker.
