# Harbor staff lifecycle synthetic verification

This implementation uses the approved Phase 1C rules. The lifecycle routes are available only with the explicit synthetic setting, a fixed loopback relying-party origin, matching disposable loopback databases for both Prisma connections, and a loopback test mailbox. Hosted deployments ignore the synthetic setting. The domain accepted by the roster and mailbox fixtures is `@staff.example.invalid`. [Owner decision and session contract](HARBOR_CONSOLE_PHASE_1C_STAFF_LIFECYCLE_DECISIONS.md)

- `/api/console/staff-lifecycle` starts and completes an administrator challenge. Each challenge expires in five minutes, is consumed on success, and binds the exact operation and target to the current Harbor login. The roster approver, designated administrators, and independent recovery approver are separate allowlists. The server rechecks the receipt, current role, roster and session version before acting.
- `/api/console/staff-lifecycle/identity` handles initial passkey enrollment, password-plus-passkey sign-in, and recovery. Invitations carry a one-time mailbox token with only its hash persisted. Possession of that token verifies the approved address. Activation consumes the token, creates a MEMBER identity, and stores the verified passkey in the same transaction. Password proof starts a separate one-use, browser-bound ceremony. The application issues a staff session only after verifying the authenticator's signature and user verification. [SimpleWebAuthn server verification](https://simplewebauthn.dev/docs/13.3.x/packages/server)
- The synthetic browser fixture issues the initial operator bootstrap tickets under distinct approved identities. Public routes can only consume a pre-authorized ticket for its exact roster identity and version. The ticket requires a new passkey and closes after use. The fixture exercises this flow before conducting the tests as the actual user or reviewer.
- Recovery requires a mailbox token and either an existing passkey or an independent reviewer attestation against an opaque case reference. Sole-owner recovery always requires the independent reviewer. Recovery consumes the token, replaces credentials and increments the account session version atomically. The audit records who requested verification, who supplied the separate approval and which account recovered. The mailbox address cannot independently authorize recovery. A credential-replacement notice contains no token.
- OWNER actions require separate designated approvers. The approval transaction rechecks the original requester, target and independent approver. Lifecycle transactions serialize the recoverable-owner invariant. When only one recoverable OWNER remains, that OWNER can request promotion of an eligible active MEMBER. An independently authorized reviewer must attest to a separate operator case before the promotion. The audit includes a reason code for each authority change. Deactivation or role changes increment the target's session version atomically. Ordinary Harbor logout continues to affect only the signed login that ended.

## Disposable application verification

Apply the checked-in lifecycle migration only to a fresh disposable database for these tests. Start the local app on `http://localhost:3054` with the same origin in `HARBOR_STAFF_LIFECYCLE_ORIGIN` and set `HARBOR_STAFF_LIFECYCLE_MODE=synthetic`. Use `http://127.0.0.1:3055/messages` for `HARBOR_STAFF_LIFECYCLE_MAILBOX_URL`. Set `HARBOR_STAFF_LIFECYCLE_ROSTER_APPROVER_IDS=lifecycle-owner-a`, `HARBOR_STAFF_LIFECYCLE_ADMIN_IDS=lifecycle-owner-a,lifecycle-owner-b`, and `HARBOR_STAFF_LIFECYCLE_RECOVERY_APPROVER_IDS=lifecycle-reviewer`.

Run `playwright test --config tests/playwright.console.config.ts staff-lifecycle.spec.ts` with `CONSOLE_BROWSER_BASE_URL` set to the same app origin, `CONSOLE_BROWSER_DATABASE_URL` set to the same disposable database, and `HARBOR_LIFECYCLE_TEST_MAILBOX` set to the mailbox URL. The test starts the loopback mailbox in memory and uses Chromium's virtual authenticator for verified WebAuthn ceremonies. The owner, reviewer and applicant exercise actual application requests. Administrator operations are available as synthetic APIs in this slice.

## Release decisions

The product owner is the initial roster approver. Before enabling real staff lifecycle, designate the trusted roster and allowed work domains, an independent sole-owner recovery approver, and the operator custody and proof-verification procedure. A real mailbox delivery adapter and the operator authorization path require separate release review. Apply the lifecycle migration only under a separate hosted migration approval. Maintain an available enrolled owner before any future change to staff login requirements.
