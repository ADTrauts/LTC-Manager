# Phase 5 — manual Facility suspension and reactivation

Status: implementation draft. The owner approved this feature after the read-only first release: OWNER-only, reasoned, reversible operational suspension; Administrator sign-in, billing, Support and existing data remain available. Scanning, staff invitations, independent recovery and assistance/grant issuance remain disabled. No tests are authorized. No merge, hosted migration or Production promotion is authorized by implementation approval.

## Canonical ownership and command

`Facility.operationsSuspendedAt` is the sole current manual-pause fact; `operationsSuspensionRevision` orders its transitions. Null means no manual pause, not that a customer is entitled or operationally ready. Existing Department, billing, partner, employment, authentication and security owners keep their decisions. Reactivation changes only these two Facility fields. It does not restore ended access, enable a Department, alter entitlements, clear a security restriction, cancel a subscription or delete anything.

The existing customer lifecycle page exposes the command only to the OWNER. The server action and transaction recheck live OWNER authority. Both suspension and reactivation require a nonempty reason (up to 1,000 characters), exact current Facility name, current OWNER password, expected revision and a UUID request reference. Password confirmation uses the existing Harbor password-account rate limiter; no recovery ceremony, staff invitation or MFA rollout is enabled. Passwords are never persisted in audit, returned to the client or included in the request fingerprint.

The command locks current staff authority, serializes exact request retries, locks the Facility, validates its current revision and rechecks the login after waiting. Same-request/same-content retries return the existing receipt without another transition or event. Conflicting reference reuse and stale forms are rejected. Repeating a suspension or reactivation against the wrong current state is also rejected. The transaction records the actual actor and Facility, operation, timestamp, reason, previous/new pause timestamps, resulting revision and request fingerprint in `HarborAuditEvent` + `HarborFacilitySuspensionAuditDetail`. Audit and Facility state commit together. A database transition trigger requires the matching current OWNER audit detail. New Facilities must start without a manual pause.

OWNERs can read the newest ten transitions with the full matching count on the Facility lifecycle page. Reasons are restricted to that page's OWNER projection. My activity adds the viewer's own suspension/reactivation events to its existing paginated customer-activity filter, without exposing reasons, other staff events or restricted assistance/staff-lifecycle history. Ordinary customer notices show only the pause and links to existing billing/Support, not internal reasons. No customer email, notification, policy deadline or automatic suspension trigger is introduced.

## Enforcement boundary

The migration attaches a row-level guard to Facility plus 93 explicitly classified operational tables. The committed migration lists the exact ownership paths. Direct Facility keys are used where present; child rows follow canonical owning parents (Records, cycles, plans, work orders, menus, assets, employees and teams), never an actor's User home Facility. Asset and Work Order alternatives cover their possible owning locations/Departments. Facility-owned Catalog definitions follow `ownerFacilityId`; globally shared platform/vendor Catalog authoring is not reclassified as Facility-owned data.

The guard checks old and new ownership when moving rows. Parent row locks hold the owning path stable. Shared Facility row locks last until commit and conflict with the suspension command's exclusive Facility lock. This design follows PostgreSQL's [row-lock semantics](https://www.postgresql.org/docs/current/explicit-locking.html#LOCKING-ROWS); it has not been exercised against a database for this draft. Operational writes arriving after a committed pause fail rather than silently succeeding or partially persisting. A transaction already holding the Facility lock completes before the pause. Infrastructure/serialization/deadlock failures remain failures; they do not authorize an exception.

The protected scopes cover Facility structure/vocabulary, Department operating configuration, workforce/schedules/Assignments/Coverage, Menus, Records and evidence/corrections/waivers, Assets/Work Orders/PM, Knowledge, operational requests and setup-import state/results. All entry points writing those tables—including direct services, organization/partner contexts, background generation, imports and offline replay—meet the same database guard. Truly unchanged updates and timestamp-only lock bookkeeping are allowed. Employee session/PIN/access-status fields remain independently governed security writes; this feature does not change them.

Billing/customer payment mirrors and entitlement reconciliation, authentication/access stores, Support, Implementation service administration, notifications and personal preferences are not operational tables in this guard. Facility billing/payment references and onboarding journey metadata are explicitly exempted. These exceptions preserve their owning authorization; they are not routes around a guarded operational write inside the same transaction. No role or database privilege is granted by the migration.

The proxy adds an early, uncached `FACILITY_OPERATIONS_PAUSED` response for customer mutation requests while preserving the existing authentication, account, billing, Help/Support and notification surfaces. This is a usability check, not the enforcement owner: a Server Action identifier posted on another allowed URL still reaches the database guard. GET/HEAD remain subject to existing read authorization. No customer session is destroyed or reminted by pausing. Existing downloads retain their previous ownership, quarantine and scanner requirements.

## Existing-data and background behavior

The internal and partner shells show a pause notice. The Dashboard stops offering Arrange and its optional settle-report request while paused. Known read-time writers—room-type backfill, missing Administrator/GM roster creation, default maintenance categories, responsible-organization defaults and daily cycle expectations—return their persisted data without creating missing operational rows. This preserves historical facts rather than manufacturing a ready/complete state. A request racing the pause can still fail and require a reload; no successful runtime behavior is claimed without execution.

PM generation and scheduled operational/notification candidate discovery skip paused Facilities. Database guards remain authoritative if state changes after candidate discovery. Existing schedules are not edited or invoked. Support automation and billing callbacks retain their existing owners and are not stopped by the Facility pause.

New offline bundles/leases are refused while paused. Server replay cannot persist operational changes during a pause. Existing local pending intent is not erased, marked accepted or converted into a new authoritative record by this feature. Disconnected devices cannot learn of a server-side pause until they reconnect. After reactivation, existing expiry, authority, revision and reconciliation rules still apply; previously queued work is not automatically approved or re-dated.

## Migration and release

One new forward migration is prepared: `20261119193000_facility_operations_suspension`. It adds nullable/defaulted Facility fields, two audit actions, their detail table and the enforcement/transition triggers. Existing migrations are unchanged. No database has been contacted or migrated for this implementation. Applying the migration initializes every Facility with no manual pause; implementation does not suspend a customer.

The new application reads require the migration. An existing unmigrated hosted Preview cannot exercise this draft, and a Ready compilation would not imply that its database is ready. Before any approved application release, use a separately approved exact database target and recovery copy, apply this forward migration, and retain the prior deployment/database pairing and existing logout receipt protections. The runtime role must retain the SELECT/row-lock privileges used by its existing writers and the new guards; no additional hosted grants are assumed or applied.

Tests, browser/app runs, fixture writes, health probes, migrations, provider events and job invocations are intentionally not performed. Local Prisma client generation is code generation only. Branch publication uses `[skip ci]`; skipped required checks are not reported as passing. Normal GitHub merge requirements remain intact; the prior one-time administrator exception for PR #43 does not apply to this draft. Any automatic Vercel Preview build is compilation only.

Future operational tables must declare their canonical Facility scope and receive a forward guard migration; do not infer coverage from the action's label or UI alone. The existing Department write manifest classifies the new OWNER command as governance. Full-customer exports and offboarding/deletion remain deferred future scope.
