## Session contract and rollout

- Each ordinary password sign-in issues a new random, signed login ID. The ordinary Harbor token has a distinct purpose from the assistance token. It cannot start or resume assistance, even if that staff member later receives a grant. Existing assistance-qualified tokens with a valid login ID keep their existing binding and still require the pilot allowlists, consent, and grant.
- A completed Harbor logout records the digest of the staff ID and login ID in the existing independent receipt table. A valid receipt invalidates that exact signed login across the proxy, shared session readers, and live authority checks in Catalog, Implementation, Support rescan, and assistance. A failed receipt write returns a retryable error and leaves the cookie in the browser. Other staff logins and Facility customer cookies are unaffected. Assistance logout still ends that login's assistance context and writes its assistance audit event in the same transaction.
- Receipts survive audit cleanup and staff deletion. The database prevents shortening, updating, deleting, or truncating a live receipt through the exact signed expiry plus the verifier's clock tolerance. Ordinary logout does not add an assistance audit event. Use the existing retention protection and keep any future cleanup separate from audit history.
- Logout and existing transactional writes that lock staff authority use compatible lock ordering under PostgreSQL READ COMMITTED. If logout commits first, a waiting action rechecks the receipt before it writes. If the action acquires the lock first, logout waits for the action. Reads and operations that only check authority at entry can finish work they authorized before logout. Private attachment reads recheck authority before returning the bytes. A fresh request with the old cookie is denied either way.
- Older ordinary cookies lack a unique login ID and require a fresh sign-in on this build. They cannot be upgraded in place. Older assistance logins already carrying valid IDs continue to use their existing receipt keys and exact expiry. The pre-1C verifier refuses the new ordinary token purpose on rollback. Avoid serving both builds during cutover. If reverting to a pre-1C release, invalidate pre-cutover staff sessions with an approved account-wide version bump before restoring traffic to it. That earlier verifier cannot enforce the new ordinary receipt rules.
- This change adds no migration. It uses the receipt table and protections introduced by `20261116220000_harbor_structure_pilot` on verified main. On a database that has yet to apply that migration, login refuses to issue a Harbor cookie, protected Harbor requests fail closed, and logout of an otherwise valid signed login reports a retryable failure. Customer auth stays independent. Confirm the existing migration ledger and receipt protections before release. [Existing database protections](../../prisma/migrations/20261116220000_harbor_structure_pilot/migration.sql)

## Decisions for the remaining lifecycle

| Decision | Recommended rule | What approval unblocks |
| --- | --- | --- |
| Invitations and activation | Require an explicit invitation from an authorized staff administrator for a verified work address. Bind the single-use invitation to its staff identity, intended role, expiry, and issuer. Start with MEMBER. Activate only after the invitee verifies the address and enrolls a second factor. Use the trusted staff roster as the source of eligibility and record who approved activation. Approve the roster owner and allowed work domains. | Staff eligibility, invitation storage and delivery, and activation. |
| Credential recovery and bootstrap | Give activated staff one-time, expiring recovery options tied to their existing account and verified factors. Rate limit and audit recovery, increment the account session version on credential replacement, and notify the staff member. Preserve bootstrap as operator-only recovery with custody, explicit authorization, and an audit trail. Require a separate recovery proof when a work mailbox is the only factor available. | Recovery proof and authorized operators, followed by reset and bootstrap changes. |
| Role changes and deactivation | Grant a specific staff lifecycle capability to designated OWNERs. Prohibit self-promotion. Require a second independent authorized OWNER for OWNER promotion, demotion, or deactivation. Revoke all affected logins with an atomic session version increment and audit the actor, target, prior and new authority, and reason. | Staff role and activation writers, authorization policy, and audit records. |
| MFA and reauthentication | Prefer passkeys or hardware security keys for staff MFA. Require a fresh second-factor check for invitations, activation decisions, credential recovery, and changes to staff authority or assistance grants. Bind the short-lived check to the current login and intended action, with a proposed five-minute validity window. | Factor enrollment, recovery-factor design, and sensitive lifecycle controls. Approve the authenticator options and step-up window first. |
| Last-owner protection | Serialize changes to owner authority and reject any transaction that removes the last active, recoverable OWNER. The first operator bootstraps one owner. Adding a second owner while only one exists requires the separately authorized and audited operator process. Keep that recovery path distinct from routine lifecycle management. | OWNER role changes, last-owner enforcement, and initial owner succession. Decide who can independently authorize recovery and what evidence they must keep. |

These choices block the corresponding lifecycle features. The per-login revocation work can be reviewed and tested while they remain open.
