## Answers to the twenty questions (compressed)

1. Experience = named unit of operational work; distinct from module/feature/tool/home/dashboard/page/engine/area.  
2. Owns product face + contracts; Overview required; tools/AI/reports optional; never owns structure/engines/warehouses.  
3. Shared shell; sections declared per Experience.  
4. Registry → Profile → Projection → Home → Engine.  
5. Catalog owns identity; Profile owns placement/config; Projection owns visibility; Engines own live values.  
6. Canonical contracts in `04`; identity/config/availability/query/workspace/nav required.  
7. Experience composes internals; Projection presence; Workspace density.  
8. Tools embedded/shared/pluggable; bindings owned by profile.  
9. Soft relationships allowed; no hard containment; no auto-enable.  
10. Navigate Area → Experience → Tool.  
11. AI optional per Experience; grounded; no inventing work.  
12. Analytics owned by Experience; roll up Area/Dept/Facility.  
13. Facility → Dept → Experience → Action → Tool → Room.  
14. Plug-in via catalog; no FB/Projection/Sidebar core changes.  
15. Projection projects Areas → Experiences → contracts — not pages/UI.  
16. Experience face / Engine SoR.  
17. BW composes compact Experience cards.  
18. Unit mounts full shells.  
19. OC aggregates status/exception contracts.  
20. Modules/top-level Logs/Knowledge/capabilities recede; engines/homes/profiles/projection survive.

## Certification statement

LTC Manager’s operational vocabulary is **Experiences**, organized by **Operational Areas**, delivered by **Projection**, composed by **Homes**, and backed by **Engines**. Tools live inside Experiences. Modules and capability checkboxes are not the constitutional model. This package is the platform definition of what an Experience is.
